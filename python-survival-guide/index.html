00 · why this page exists

The other guides in this series make your machine reproducible, your history safe, your pipeline honest, and your jobs survivable. This one is about the thing inside all of them: the Python itself, and whether it reads like Python or like a language you used to know, transcribed.

This page will not teach you to program; it assumes you already write Python that runs. What it is: a reference for the idioms that separate "works" from "Pythonic," and a gallery of the habits — usually imported from Java, C, or MATLAB — that make a reviewer sigh before they comment. It deliberately stops at the language's edge: testing, typing discipline, logging and project structure live in the pipeline and setup guides, and this page links there rather than repeating them.

"Pythonic" is not a personality trait or gatekeeping. It's a real property: code that uses the language's own grain — its data model, its built-ins, its idioms — so the next reader (you, in three weeks) spends their attention on the logic, not on decoding the style.

>>> 01 · the_daily_loop · write · run · refactor

01 · day zero: the loop

Idiomatic Python isn't written, it's rewritten. The loop: get it working plainly, then let the language collapse the boilerplate — a loop becomes a comprehension, a try/finally becomes a with, a tuple-returning function becomes a dataclass. The REPL and a good editor make each step cheap to check.

▶ make it work (fine, for now) 
# sum the value of QUOTED shipments
total = 0
for s in shipments:
    if s["status"] == "QUOTED":
        total = total + s["value_eur"]
✓ then make it Python 
# the same thing, in the language's grain
total = sum(
    s["value_eur"]
    for s in shipments
    if s["status"] == "QUOTED"
)
IF YOU ONLY REMEMBER THREE THINGS

① There is almost always a built-in or stdlib function for what your loop is doing — look before you loop. ② Readability counts (it's line 7 of the Zen) — clever one-liners that need a comment to decode are not the win they feel like. ③ Name your data. A dict with fixed keys passed through five functions wants to be a dataclass.

02 · what "Pythonic" actually means

Python was released in 1991 by Guido van Rossum, named after Monty Python, not the snake — which is why the docs have always had a sense of humour and why "spam" and "eggs" are the canonical variable names. Its defining bet, unusual for its era: that code is read far more often than it's written, so the language should optimise for the reader. Significant whitespace, one obvious way to do things, batteries included — all downstream of that one decision.

The closest thing to an official definition of taste is the Zen of Python — type import this into any REPL and Tim Peters' 19 aphorisms print out. The load-bearing ones for daily work:

  • Beautiful is better than ugly · Readable counts. The reader is the customer.
  • There should be one — and preferably only one — obvious way to do it. When you feel clever, you're often off the path.
  • Explicit is better than implicit · Flat is better than nested. Surprises and deep indentation are both smells.
  • Special cases aren't special enough to break the rules — although practicality beats purity. The escape hatch that keeps the Zen from being dogma.

"Pythonic" just means: written the way the language and its community have agreed reads best. It's conventional, not moral — but the conventions are codified (PEP 8 for style, PEP 20 for philosophy) and your linter enforces most of them, so you don't have to argue about them in review.

>>> 03 · the_data_model · __dunder__

03 · the mental model: it's dunders all the way down

Naive model: "Python has special syntax — len(), for, +, in, with — that works on the built-in types." Real model: that syntax is a thin skin over methods you can implement yourself. len(x) calls x.__len__(). a + b calls a.__add__(b). for i in x calls x.__iter__(). with x calls x.__enter__() and __exit__(). This is the data model, and understanding it is the difference between using Python and reading it fluently.

The payoff is twofold. First, reading: when you see with open(...), you know a context manager guarantees cleanup; when you see for x in thing, you know thing is iterable, not necessarily a list. Second, writing: make your own class support len(), iteration, or [] by implementing the dunder, and it behaves like a native type — duck typing means Python never checks the class, only whether the method exists.

DUCK TYPING, IN ONE LINE

"If it walks like a duck and quacks like a duck, it's a duck." Python doesn't ask what type something is; it asks what it can do. A function that does for x in thing works on a list, a file, a generator, or your custom class — anything with __iter__. This is why idiomatic Python checks for behaviour (or just tries it — see EAFP), not type.

>>> 04 · core_reference · the idioms

04 · core reference: the idioms that earn their keep

comprehensions — the loop that builds a thing

If a loop exists only to build a list, set, or dict, it wants to be a comprehension: one expression that says what you're building instead of how. The reader sees the shape of the result immediately.

▶ the accumulator loop 
regions = []
for s in shipments:
    if s.value_eur > 1000:
        regions.append(s.region)
✓ the comprehension 
regions = [
    s.region for s in shipments
    if s.value_eur > 1000
]

Same for {...} (set), {k: v ...} (dict), and (...) — but the parenthesised form is a lazy generator, not a tuple comprehension (there's no such thing). The one rule: if it doesn't fit on a couple of readable lines, write the loop. A triple-nested comprehension with two conditions is a write-only artifact.

unpacking — stop indexing

# tuple unpacking: name the parts, don't index them
first, last = full_name.split(" ", 1)        # not name[0] / name[1]
a, b = b, a                                  # swap, no temp variable

# star-unpacking: head and the rest
winner, *runners_up = ranked_ports          # runners_up is a list of the remainder

# in a loop, with enumerate — never `for i in range(len(x))`
for rank, port in enumerate(ranked_ports, start=1):
    print(rank, port)

# walk two sequences together with zip
for port, quote in zip(ports, quotes):
    record(port, quote)

context managers — let with do the cleanup

Anything that must be opened and closed, acquired and released, set up and torn down — a file, a lock, a DB connection, a timer — belongs in a with block. It guarantees the teardown runs even if the body raises, which a manual try/finally also does but more verbosely and more forgettably.

▶ manual, leaks on error 
f = open("quotes.csv")
data = f.read()
f.close()   # skipped if read() raises
✓ with: always closed 
with open("quotes.csv") as f:
    data = f.read()
# f is closed here, even on error

You can write your own context manager with one decorator — no class, no __enter__/__exit__ methods. The whole shape pivots on the single yield: code before it is the setup, the with body runs at it, and code after it is the teardown. Wrapping the yield in try/finally is what guarantees the teardown runs even when the body raises — the entire reason to use a context manager instead of just calling two functions.

from contextlib import contextmanager
import time

@contextmanager
def timed(label):
    start = time.perf_counter()      # 1. SETUP  (the __enter__)
    try:
        yield                        # 2. the `with` body runs here
    finally:
        elapsed = time.perf_counter() - start   # 3. TEARDOWN (the __exit__),
        print(f"{label} took {elapsed:.3f}s")    #    runs even if the body raised

# using it reads like any built-in `with`:
with timed("price quotes"):
    price_all_quotes()               # → "price quotes took 0.412s"

build strings with f-strings

An f-string (the f prefix, since Python 3.6) embeds expressions directly in the string: {name} is replaced with the value of name. Prefer it over the older alternatives for three concrete reasons, not just taste:

  • Readable — the values appear where they'll print, so you read the output left to right instead of cross-referencing a %-tuple or counting + joins.
  • No str() dance — it calls str() on each value for you, so concatenation's classic TypeError: can only concatenate str (not "float") simply can't happen.
  • Fastest — f-strings are evaluated at compile time into efficient bytecode; they beat %, .format(), and +-concatenation in benchmarks.
name, total = "Nimbus", 1042.5
# no  — manual str(), easy to typo the spacing/colons:
"Total for " + name + ": " + str(total)
# no  — %-formatting: values live in a separate tuple, read out of order:
"Total for %s: %s" % (name, total)
# yes — values inline; :,.2f formats in place (thousands sep, 2 decimals):
f"Total for {name}: {total:,.2f}"     # → 'Total for Nimbus: 1,042.50'
# bonus — the = suffix prints name AND value, the fastest debug print there is:
f"{total=}"                           # → 'total=1042.5'
THE ONE PLACE NOT TO USE THEM

Never f-string user input into SQL, shell commands, or HTML — f"SELECT * FROM t WHERE id = {user_id}" is an injection hole. Use the library's parameterisation (the pipeline guide's security note). f-strings are for display, not for building queries.

>>> 05 · structuring_data · dict vs dataclass

05 · structuring data: stop passing dicts around

A dict with a fixed, known set of keys that travels through several functions is a class wearing a disguise. Every access is a stringly-typed gamble (s["valeu_eur"] fails at runtime, not in your editor), nothing is discoverable by autocomplete, and the "shape" lives only in your head. A dataclass fixes all three for the cost of a decorator.

▶ the dict that should be a type 
s = {"id": "NF-1042",
     "value_eur": 1000.0,
     "region": "ECA"}
# typo not caught till runtime:
total = s["valeu_eur"]   # KeyError
✓ a dataclass: typed, autocompleted 
from dataclasses import dataclass

@dataclass(frozen=True, slots=True)
class Shipment:
    id: str
    value_eur: float
    region: str

s = Shipment("NF-1042", 1000.0, "ECA")
s.value_eur        # editor knows this field

frozen=True makes instances immutable (hashable, safe to share — the same instinct the Spark guide has about immutability); slots=True makes them smaller and faster and blocks typo-attributes. You get __init__, __repr__, and __eq__ for free.

THE BOUNDARY RULE (shared with the pipeline guide)

Validate the messy outside world once, at the door, with pydantic; pass typed objects (dataclasses) around inside, where the data is already trusted. A dict of unknown shape three call-frames deep is where bugs go to hide.

>>> 07 · the_most_wanted · # 8 at large

07 · the most wanted

Eight habits that run fine and read like a confession that you learned a different language first.

★ WANTED ★🔢

The Range-Len Looper

Crime: for i in range(len(items)): then items[i] — index bookkeeping to avoid just iterating the thing.

THE FIXfor item in items, or enumerate(items) when you truly need the index.
★ WANTED ★💥

The Bare Excepter

Crime: except: (or except Exception: pass) — swallows everything including KeyboardInterrupt and the bug you'll spend a day hunting.

THE FIXCatch the specific exception you can handle; let the rest propagate. Never pass silently.
★ WANTED ★🧨

The Mutable Default

Crime: def f(x, acc=[]): — the list is created once, at definition, and shared across every call. State leaks between unrelated calls.

THE FIXdef f(x, acc=None): then acc = acc or [] inside. (Bugbear flags this as B006.)
★ WANTED ★➕

The String Concatenator

Crime: building a string in a loop with +=, or a message with "a" + str(x) + "b". Quadratic and unreadable.

THE FIX"".join(parts) for loops; f-strings for messages.
★ WANTED ★🗝️

The Key Checker

Crime: if k in d: x = d[k] else: x = default — two lookups and three lines for one idea.

THE FIXd.get(k, default). For accumulation, defaultdict or d.setdefault.
★ WANTED ★🏷️

The Type Comparator

Crime: if type(x) == list: or checking == True. Fights duck typing and breaks on subclasses.

THE FIXisinstance(x, list) if you must; better, just try the operation (EAFP). if x: for truthiness.
★ WANTED ★🐫

The camelCase Defector

Crime: def getQuoteTotal(shipmentList): — Java naming smuggled across the border.

THE FIXsnake_case for functions and variables, PascalCase for classes. PEP 8, enforced by Ruff.
★ WANTED ★📥

The Star Importer

Crime: from pandas import * — pollutes the namespace, hides where names come from, shadows built-ins silently.

THE FIXimport pandas as pd; import the specific names you use. Explicit beats implicit.

>>> 08 · the_eternal_debate · EAFP vs LBYL

08 · the eternal debate: EAFP vs LBYL

LBYL 👀 — look before you leap

Check preconditions first: if k in d and d[k] is not None and ...: then act. Familiar to most languages.

Fails when: the checks race against reality (the file exists at check, gone at open), and the guard ladder buries the one line that does the work.

EAFP 🙏 — easier to ask forgiveness

Just try it, handle the exception if it fails: try: x = d[k] except KeyError: .... The Pythonic default.

Fails when: overused as flow control for the common case, or the try wraps so much code you can't tell which line you're forgiving.

▶ LBYL: racey, noisy 
if os.path.exists(path):
    if os.access(path, os.R_OK):
        with open(path) as f:
            data = f.read()
    else:
        data = None
else:
    data = None
✓ EAFP: the Pythonic reflex 
try:
    with open(path) as f:
        data = f.read()
except OSError:
    data = None
THE RULE

EAFP by default — it's more Pythonic, faster on the happy path, and immune to check-then-act races. Keep the try block to the single line that can fail, and catch the specific exception. Reach for LBYL only when the failure is genuinely expected and common enough that exceptions-as-flow-control would dominate — practicality beats purity.

>>> 09 · traceback_sos · Traceback (most recent call last)

09 · SOS — read the traceback, it's telling you

A traceback isn't noise to scroll past — it's a precise map. Read it bottom-up: the last line is the exception and message (what went wrong); the lines above are the call stack (how you got there), most-recent last. Find your scenario.

"KeyError / AttributeError from a dict I passed around"

The Key Checker and the dict-instead-of-dataclass posters, billed. A typo'd key or a missing field that an editor would have caught if the data were typed. Short term: d.get(k). Real fix: make it a dataclass (stage 05) so the typo is a red squiggle, not a 3am page.

"UnboundLocalError — but the variable clearly exists"

You assigned to a name anywhere in the function, so Python treats it as local everywhere in that function — including before the assignment. Usually an x = x + 1 where you meant to read an outer x. Fix: pass it in as an argument, or (rarely) global/nonlocal if you genuinely mean to rebind an outer name.

"my default argument remembers things between calls"

# the Mutable Default poster, in the wild:
def add_quote(q, batch=[]):    # `batch` is ONE list, made at def-time
    batch.append(q)
    return batch
add_quote("a")                 # ['a']
add_quote("b")                 # ['a', 'b']  ← surprise: same list

# fix:
def add_quote(q, batch=None):
    batch = batch if batch is not None else []
    batch.append(q)
    return batch

"it's a copy... but editing one changed the other"

# assignment binds a NAME to an object; it does not copy the object.
a = [1, 2, 3]
b = a            # b and a are the SAME list
b.append(4)      # a is now [1, 2, 3, 4] too

import copy
b = a.copy()              # shallow copy — new list, same inner objects
b = copy.deepcopy(a)      # deep copy — fully independent, for nested structures

"ModuleNotFoundError / circular import"

Two flavours. ModuleNotFoundError usually means the wrong interpreter/venv (the setup guide's first-aid: which -a python, rebuild the venv). A circular import means module A imports B which imports A at load time — the fix is structural: move the shared thing to a third module, or do the import inside the function that needs it.

🚨 THE GOLDEN RULE

Read the traceback bottom to top, out loud if you must, before you change a line. The exception type and the last frame name the bug ~80% of the time. Changing code before reading the traceback is debugging with your eyes closed — and the print-debugging loop the setup guide warns about starts exactly here.

bonus weapon: the REPL and breakpoint() 🔬

    return quote.value * rate

>>> 10 · boss_fight · 0/5

10 · boss fight 🐉

Five questions between you and the rank of Benevolent Dictator. import this is watching.

1/5 · You need a list of names from records where value > 1000. The Pythonic form?

The comprehension says what you're building. The map/filter/lambda chain is technically equivalent but harder to read — and the loop is three lines for one idea.

2/5 · def f(x, items=[]): — what's wrong?

The classic mutable-default trap. Default args evaluate once, at def-time. Use None as the sentinel and create the list inside.

3/5 · Reading a file that might not exist — the Pythonic approach?

EAFP avoids the check-then-act race (the file can vanish between exists() and open()) and keeps the happy path clean. Catch the specific exception.

4/5 · A record with fixed fields (id, value, region) passed through five functions should be…

Fixed shape = a type. The dataclass gives you typed fields, __repr__, __eq__, and turns the runtime KeyError typo into an editor squiggle.

5/5 · a = [1,2,3]; b = a; b.append(4) — what is a?

Assignment binds a name to an object; it doesn't copy. b and a point at one list. Use a.copy() (or copy.deepcopy for nested data) for independence.
