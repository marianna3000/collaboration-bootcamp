step 00/1300_why_this_existsexit 0

Why this page exists

This page will not make you a better engineer by itself. Nothing you can read in twenty minutes will. What it is: a map of the mistakes consultants make with their own machines and habits, and the shortest known route out of each one — written for the two moments that actually matter: the Sunday before a client kickoff, and the Tuesday when nothing imports.

Consulting has a property product teams don't: you change environments constantly. New client, new repo, new VPN, new proxy, new rules. A product engineer can afford a hand-crafted machine that took three years to evolve. You can't — your setup gets stress-tested every few months, usually on a deadline. The thesis of this guide is one sentence: your development environment is a deliverable. Treat it like one — versioned, documented, reproducible.

Scope: getting the most from your IDE, working with your terminal instead of against it, the software engineering basics clients silently judge you on, Python tooling done the current-decade way, the ways-of-working vocabulary — Scrum, TDD, design docs, scope control — that clients assume you already speak, and just enough containers to keep your laptop clean. Spark gets its own dedicated module in this series.

step 01/1301_the_daily_loopexit 0

Day zero: the loop you run every day

Strip away the client logos and every productive day is the same eight steps. The whole point of a good setup is that steps 1–4 take minutes, not a day of Slack archaeology.

$ git clone git@ssh.dev.azure.com:v3/nimbus-freight/logistics/nimbus-pricing && cd nimbus-pricing
$ mise install            # reads .mise.toml → exact python/node, no guessing
$ uv sync                 # reads uv.lock → identical deps to everyone else
$ direnv allow            # loads project env vars the moment you cd in
$ git switch -c feat/surcharge-rules
# ... edit; ruff fixes on save; tests in the sidebar ...
$ uv run pytest -x        # -x: stop at first failure, fix, repeat
$ git add -p              # stage hunks, not 'add .' — review yourself first
$ git commit -m "feat: apply surcharge rules to spot quotes"
$ git push                # open PR; small diff, reviewable in one coffee
IF YOU ONLY REMEMBER THREE THINGS

1. If it isn't in a file, it doesn't exist. Tool versions, deps, env vars — declared, committed, reproducible.

2. Pin everything. "latest" is not a version, it's a countdown.

3. Small commits, small PRs. Nobody can review 2,000 lines; everybody approves them anyway. That's the problem.

step 02/1302_what_a_setup_isexit 0

What a "setup" actually is

The ideas here are older than the cloud, older than Python, in some cases older than your firm. Unix (1969) established the philosophy this guide leans on: small programs that do one thing well, composed through a universal text interface. The terminal you're avoiding is not legacy — it's the only interface that has survived every platform shift since, precisely because everything composes with everything.

The "dotfiles" culture — versioning your ~/.zshrc, ~/.gitconfig and friends in a git repo — formalized in the 2000s, and the cloud era added the final piece: declarative environments. Terraform did it for infrastructure; Brewfile, .mise.toml and uv.lock do it for your laptop. Same idea, smaller blast radius: describe the desired state in a file, let a tool converge reality to it.

A "setup", then, is not the apps you've installed. It's the set of files from which your working machine can be regenerated. Everything not covered by those files is improv — and improv is what you were doing at 11pm before your last kickoff.

(Yes, the terminal turned 55 and still ships faster than most UIs. It has seniority. Respect it.)

step 03/1303_mental_modelexit 0

Mental model: snowflake vs bootstrap

The naive model says a machine is configured once: install things until it works, then never touch anything because nobody remembers why it works. That machine is a snowflake — unique, beautiful, and it melts the moment it meets a new laptop, a new teammate, or an OS update.

The real model treats your machine as derived state. The source of truth is a handful of small files in version control; the laptop is just a cache that can be rebuilt. The difference shows up exactly when you can least afford it: hardware death, client-issued laptop, "can you get Alex productive by Thursday?"

One corollary worth internalizing: in the bootstrap model, fixing something twice is a bug. The second time you adjust a setting by hand, it goes into the dotfiles repo instead. That single habit compounds more than any tool on this page.

Software engineering basics clients judge you on

None of this is glamorous. All of it is visible in your first week's PRs, and it travels further than any architecture diagram:

  • Commit messages tell a story. Use Conventional Commits (feat:, fix:, chore:): grep-able history, automatable changelogs, and reviewers who can navigate your branch. Everything deeper about git itself — branching, rebasing, recovery — lives in this series' Git Survival Guide.
  • PRs under ~400 lines. Review quality falls off a cliff beyond that; split by commit or by stacked PRs.
  • Tests are the spec. A failing test that reproduces the bug, then the fix. The discipline matters more than the coverage number.
  • Decisions get written down. A one-page ADR ("we chose X over Y because Z") saves the next consultant — often future-you — a week of reverse engineering.
  • KISS & YAGNI. Build for the problem at hand. You cannot predict the client's roadmap; their own PM can't either.
  • Least Surprise. Choose the solution everyone can understand over the clever one. Does it really need a specialized database? If measurements say so, yes; otherwise, no.
  • DRY — with the Rule of Three. Don't repeat yourself, but don't abstract on the second occurrence either; the wrong abstraction costs more than duplication. Extract on the third.
  • Prefer composition to inheritance, and immutable to mutable. Both make code easier to reason about, test, and scale. A corollary your on-call self endorses: never operate something you didn't build — if it isn't your code, it should be a managed service.
  • Exit codes and streams are the API of your scripts. Output to stdout, logs to stderr, exit 0 on success, non-zero on failure — schedulers and CI act on these, and "it failed silently with exit 0" is a genuinely embarrassing incident review.

step 07/1307_ways_of_workingexit 0

Ways of working: Agile, Scrum, TDD & writing decisions down

Nobody fails an engagement over a missed keyboard shortcut. People do fail them by sitting in sprint planning without knowing what a sprint is, or by treating "we do Scrum here" as background noise. As a consultant you don't choose the client's process — you walk into one mid-flight. This section is the vocabulary and the moves, compressed.

Agile is the values; Scrum is a framework; Kanban is the other one

Agile is four sentences from 2001 (the Manifesto): individuals over processes, working software over documentation, collaboration over contracts, responding to change over following a plan — each valuing the left more, not the right not at all. Scrum is the most common framework implementing it, and the default at most clients — Azure DevOps even ships a Scrum process template. Kanban is the flow-based alternative: no sprints, just a board with WIP limits; common for ops-flavored and support-heavy teams. The whole of Scrum fits in one table:

3 roles3 artefacts5 events
Product Owner — owns the vision, represents stakeholders, orders the backlogProduct Backlog — the prioritized list of everything wantedSprint — the time-box itself (1–4 weeks)
Scrum Master — facilitates the process, removes obstacles (not a project manager)Sprint Backlog — what the team committed to this sprintPlanning — decide what goes in · Daily Scrum — sync, ≤15 min
Development Team — self-organizing; does the workIncrement — the potentially shippable product at sprint endReview — demo what shipped · Retrospective — improve the process

The three principles underneath — transparency, inspection, adaptation — are the actual point; the ceremonies are just scaffolding for them. Consultant survival notes: in the daily, answer yesterday / today / blockers in thirty seconds — it's a synchronization, not a status novel. Treat the retrospective as the highest-leverage meeting of the sprint; it's where you, the outsider, can legitimately improve the client's process. And know the term Definition of Done — the team's checklist for "actually finished" (reviewed, tested, deployed via pipeline), because "done" without one means five different things to five people.

One more acronym for regulated or hardware-adjacent clients: CMMI — a five-level process maturity model (Initial → Managed → Defined → Quantitatively Managed → Optimizing). You'll rarely run it, but when a client says "we're aiming for Level 3", you should know they mean defined, repeatable processes — and expect more ceremony, not less.

TDD: red → green → refactor

Test-Driven Development inverts the order you were probably taught: write the failing test first, write just enough code to pass it, then refactor with the test as your safety net — and loop. Test and production code grow simultaneously, which is the trick: coverage stops being homework done after the fact, and the tests pressure your design toward small, simple units (TDD is where KISS and YAGNI from step 04 stop being posters and start being enforced).

Honest framing so you don't oversell it in a steering meeting: TDD is a design discipline, not a coverage quota. A team can hit 95% coverage writing tests last and still have untestable spaghetti; a team doing TDD gets testable design as a side effect. And it pairs naturally with the bug-fix rule from step 04: a failing test that reproduces the bug, then the fix.

Recording decisions: design docs & ADRs

Every system is a pile of trade-offs; the expensive failure mode is a pile of undocumented trade-offs. Two instruments, different altitudes. The ADR (one page, per decision — "we chose X over Y because Z") you met in step 04. The Software Design Document is the bigger sibling, written before a significant build, and its skeleton is worth memorizing: context & scope (what we're solving and why), goals and non-goals (measurable impact — and the things you're deliberately ignoring, which is the part juniors skip), proposed solution (high level, big picture, no code), alternatives considered (and why discarded), dependencies. Outcome-focused, no pseudocode. As the consultant, you're often the only person in the room paid to write this — do it well and it outlives the engagement.

Scope creep: the disease consultants are paid to catch early

Every project drifts beyond its original scope unless something pushes back — and the pushing back is, frankly, part of what you bill for. The toolkit, compressed: MoSCoW the backlog — Must-have, Should-have, Could-have, Won't-have — and write the Won'ts down, because an undocumented Won't is next sprint's Must. Route every new ask through change control, however lightweight: "good idea — onto the backlog, we'll weigh it at planning" is a complete sentence that protects the timeline and the relationship. Think MVP: a polished core beats a bloated product with half-implemented everything. And when a stakeholder pushes, don't argue — itemize the trade-off: "we can add X; which Must-have moves out to pay for it?" Scope creep survives on invisible costs. Your weapon is a visible bill.

PROCESS GUARDRAILS YOU'LL MEET AT MATURE CLIENTS

At least two reviewers on every PR; nothing reaches an environment except through the CI/CD pipeline (no laptop deploys, ever); and semantic versioning on anything other teams consume — MAJOR.MINOR.PATCH, where MAJOR means "this will break you". When you find these missing, that's not freedom — it's your first recommendation slide.

step 08/1308_containers_localexit 0

Containers on your machine

This is the laptop half of containers — running them as disposable dependencies and writing one honest Dockerfile. Image hardening, multi-stage builds, registries, scanning, healthchecks, immutable deployments: that's deployment territory — a different bootcamp's turf, deliberately out of scope here. Here, containers earn their place the same way mise and uv did — they make your environment declarative: the database your project needs is a file in the repo, not an installation ritual.

First, the licensing trap

DOCKER DESKTOP IS NOT FREE AT YOUR CLIENT

Docker Desktop requires a paid subscription for commercial use in companies above roughly 250 employees or $10M revenue — which describes most clients. Installing it casually on a client-issued laptop is a license violation with your name in the audit log. The engine itself is open source; it's the Desktop app that's licensed. Alternatives that run the same containers: OrbStack (macOS, fast, paid for commercial use but cheap), Colima (free, CLI-only, macOS/Linux), or whatever the client has standardized on — ask before installing anything.

The pattern that earns rent: compose for local dependencies

"I need a Postgres for five minutes" should never end in a native install. A compose.yaml in the repo means every teammate gets identical services, and deleting them leaves no residue:

# compose.yaml — committed; the project's local dependencies, declared
services:
  db:
    image: postgres:16.4        # pinned, like everything else on this page
    environment:
      POSTGRES_PASSWORD: localdev   # local-only creds; real ones live in .env
    ports: ["5432:5432"]
    volumes: ["pgdata:/var/lib/postgresql/data"]
volumes:
  pgdata:

# daily verbs:
$ docker compose up -d          # dependencies appear
$ docker compose down           # dependencies vanish; data survives in the volume
$ docker compose down -v        # ...and the data too. Fresh start.

One honest Dockerfile for a uv project

The only container-build idea you must internalize at laptop scale is layer caching: copy the lockfiles and install dependencies before copying your code, so editing code doesn't reinstall the world.

# Dockerfile — minimal and correct for a uv project
FROM python:3.12-slim
COPY --from=ghcr.io/astral-sh/uv:0.11.20 /uv /uvx /bin/   # pin the uv tag

WORKDIR /app
# deps layer first: changes rarely, caches almost always
COPY pyproject.toml uv.lock ./
RUN uv sync --locked --no-install-project --no-dev
# code layer second: changes constantly, rebuilds alone
COPY . .
RUN uv sync --locked --no-dev

CMD ["uv", "run", "python", "-m", "nimbus_pricing"]
# and add .venv to .dockerignore — your local env must never enter the image

Hygiene, or: the 41 GB you forgot about

Containers accumulate silently. docker system df shows the damage; docker system prune clears stopped containers and dangling images (safe — anything you need gets re-pulled); docker system prune -a --volumes is the full reset — it also deletes named volumes, i.e. your local databases, so read the prompt. Put a quarterly reminder on it; your future SSD says thanks.

DEPLOYMENT-GRADE CONTAINERS ARE A DIFFERENT BOOTCAMP

Multi-stage builds, non-root users, image scanning, healthchecks, registries and immutable deployments are deliberately absent here — they're system-scale concerns, out of this series' scope. The one rule that bridges both worlds: containers log to stdout/stderr, never to files — the streams-as-API rule from step 04, containerized. Windows colleagues: Docker engines run inside WSL2; same rules apply.

step 10/1310_notebooks_vs_scriptssettled

The eternal debate: notebooks vs scripts

Sixty seconds, settled. Both sides are right — about different phases of the work.

📓 Notebooks

  • Unbeatable for exploration: see the data, iterate, plot
  • The right medium for analysis you'll show
  • But: hidden state, out-of-order execution, unreviewable diffs, untestable

📜 Scripts / packages

  • Testable, diffable, importable, schedulable
  • CI can run them; reviewers can review them
  • But: slower to iterate when you don't yet know what you're building

The one rule: the moment a notebook gets scheduled, it's a script with worse diffs. Promote it — extract the logic into a tested module, keep the notebook as the lab journal it was born to be.

step 11/1311_disaster_recoveryexit 1 — read calmly

Disaster recovery

You panicked, you clicked the button, here you are. Breathe. Each recipe: the situation, the commands, the caveat.

"Nothing imports and which python is lying to me!"

Imports fail, the wrong Python answers, three package managers are fighting over PATH.

$ which -a python python3        # see ALL pythons on PATH, in resolution order
$ mise doctor                    # is mise activated in this shell? shims healthy?
$ cd your-project && mise install # converge to the project's pinned version
$ rm -rf .venv && uv sync        # rebuild the env from the lockfile — 30 seconds
$ uv run python -c "import sys; print(sys.executable)"  # verify it's .venv's python

Caveat: if an old conda init block in your ~/.zshrc is hijacking PATH, comment it out — conda's auto-activate is the usual saboteur on consultant machines.

"I committed a secret!"

An API key / connection string is in a commit. Maybe pushed. Maybe ten minutes ago.

# STEP 0 — rotate the credential. Now. Before any git surgery.
# the key is compromised the moment it left your machine; history-cleaning is hygiene, not the fix
# full history-surgery procedure (git-filter-repo, coordinating the force-push,
# team re-clones): see the Git Survival Guide — link below
# then prevent the sequel, which IS a setup concern:
$ echo ".env" >> .gitignore
$ uvx pre-commit install      # the gitleaks hook from step 06 now guards every commit
GOLDEN RULE

Rotate first. Deleting the commit does not un-leak the secret. Forks, clones, CI caches and scrapers may already have it — on public GitHub, leaked keys get exploited in minutes, not days.

"VS Code's Discard All Changes deleted my untracked files!"

You wanted a clean tracked state; the editor also removed files git never knew about.

# untracked = no git safety net. Your hopes, in order:
# 1. VS Code Local History: open Timeline view on the file's old location,
#    or Command Palette → "Local History: Find Entry to Restore"
# 2. Anything once STAGED may survive inside git — dangling-blob recovery
#    is git surgery: see the Git Survival Guide, linked below
# 3. Editor/OS backups (Time Machine etc.) — your last resort

Caveat: sometimes the honest answer is the file is gone. The durable fix is habitual: commit early and often on a branch — WIP commits are free, squash later.

"The client network blocks every install!"

Corporate proxy with TLS inspection; pip/uv/git all fail with certificate errors.

# 1. Get the corporate root CA cert from client IT (a .pem/.crt file) — the clean fix
$ export SSL_CERT_FILE=/path/to/corp-root-ca.pem      # honored by uv and most tools
$ export REQUESTS_CA_BUNDLE=/path/to/corp-root-ca.pem # python requests
# 2. Client runs an internal index (on Azure that's an Azure Artifacts feed)? Point at it:
#    [[tool.uv.index]] in pyproject.toml with the internal index URL
# 3. Truly air-gapped: export the lockfile, fetch wheels outside, carry them in
$ uv export --format requirements.txt -o requirements.txt
$ pip download -r requirements.txt -d ./wheels        # on the machine WITH internet
$ uv pip install --no-index --find-links ./wheels -r requirements.txt   # inside

Caveat: resist --insecure / disabling TLS verification. It "works", it lingers in your config forever, and it's exactly the finding a client security review exists to catch.

"It works on my machine but not in CI!"

Green locally, red in the pipeline. The classic.

$ git status --ignored | head -30   # is CI missing a file you never committed? (.env, fixtures)
$ git stash -u && uv run pytest     # test what's COMMITTED, not what's lying around
$ rm -rf .venv && uv sync --frozen && uv run pytest  # exact lockfile env, like CI builds
$ git stash pop                     # carry on

Caveat: 90% of "works on my machine" is one of three: an uncommitted file, an env var only your shell has, or a dependency installed outside the lockfile. The recipe above flushes out all three.

BONUS WEAPON: py-spy

A process hangs — local script, stuck pipeline, mystery job — and you have no idea where. py-spy attaches to a running Python process and shows you, without restarting or instrumenting anything:

uvx py-spy dump --pid 12345 — instant stack trace of where it's stuck. uvx py-spy top --pid 12345 — live, htop-style view of which functions burn CPU. The single best "why is it hanging" tool in the Python toolbox, and it works in production.
