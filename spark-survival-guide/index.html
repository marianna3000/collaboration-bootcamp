stage 00/11 · why_this_exists · 8/8 tasks · 0.4 s

00 · why this page exists

By now you have a reproducible machine, a history you can't lose, and a CI pipeline that catches your optimism. This module is for the day the data outgrows the machine: one process becomes a cluster, and your bug reports start containing the word executor.

This page will not teach you distributed computing by itself; it is the reference you open when the job that ran fine for six months suddenly takes four hours, and a map of the mistakes everyone makes between "it's just pandas with different syntax" (it is not) and reading a query plan without flinching.

It is written vendor-neutral: everything here is plain PySpark and works on Databricks, EMR, Dataproc, or your laptop. Where Databricks reality differs, you'll see a labelled note — because most of our clusters live there, but the concepts must not.

stage 01/11 · the_daily_loop · 8/8 tasks · 1.2 s

01 · day zero: the loop

Strip away the cluster and every PySpark day is the same loop: build lazily, peek cheaply, run small, then scale. The whole art is keeping steps 2–5 fast on a sample so step 6 doesn't surprise you at full size.

# the loop, as a session — Nimbus Freight nightly quote pricing
from pyspark.sql import SparkSession, functions as F

spark = SparkSession.builder.appName("nightly_quotes").getOrCreate()

# reading defines the data; it does not load it. nothing has run yet.
shipments = spark.read.parquet("s3://nimbus-lake/shipments/")   # 2.1B rows
ports     = spark.read.parquet("s3://nimbus-lake/dim_ports/")   # 4,800 rows

# every line below is LAZY — it grows the plan, runs nothing
priced = (shipments
    .where(F.col("status") == "QUOTED")
    .join(F.broadcast(ports), "port_id")    # broadcast = no shuffle (ports is tiny)
    .withColumn("surcharge_eur", F.col("value_eur") * F.col("surcharge_rate"))
    .groupBy("region")                      # this one WILL shuffle
    .agg(F.sum("surcharge_eur").alias("total_surcharge")))

# read the plan BEFORE you pay for it
priced.explain("formatted")

# peek: runs a tiny slice, not the world
priced.limit(20).show()

# THE action — this is the line that actually runs everything above
(priced.write
    .mode("overwrite")
    .parquet("s3://nimbus-lake/marts/surcharge_by_region/"))
IF YOU ONLY REMEMBER THREE THINGS

① Nothing runs until an action — your "fast" code is fast because it did nothing. ② The cost of a job lives in its shuffles — know which lines cause them. ③ Never collect() anything you haven't counted first — the driver is one machine, and it is not a big one.

stage 02/11 · what_spark_is · 8/8 tasks · 2.0 s

02 · what Spark actually is

Spark was born in 2009 at UC Berkeley's AMPLab, open-sourced in 2010, and became a top-level Apache project in 2014 — which makes it old enough to have opinions and young enough that half its defaults changed last release. It exists because of MapReduce: Google's 2004 paper made cluster computing possible, and a decade of writing MapReduce jobs made everyone wish it were also pleasant. Spark's pitch was simple: keep data in memory between steps instead of writing to disk after every map and reduce, and give humans an API above the plumbing.

What it is today, in one sentence: a distributed query engine with a compiler in the middle. You write DataFrame code (or SQL — same thing, see the debate); the Catalyst optimizer rewrites it into a physical plan; the scheduler chops the plan into stages and tasks; executors run the tasks. Three design principles fall out of its history and explain most of its behavior:

  • Lazy evaluation. Transformations build a plan; only actions execute it. This lets the optimizer see your whole query before running any of it — and lets you build a 40-line pipeline that "runs" in 0.2 seconds because it hasn't.
  • Immutability + lineage. DataFrames are never modified, only derived. If an executor dies, Spark recomputes its partitions from lineage instead of restoring a backup — fault tolerance by recipe, not by copy.
  • Data parallelism over partitions. Every DataFrame is split into partitions; every task processes one partition. Parallelism, skew, and most performance mysteries are partition stories.
DATABRICKS REALITY

Databricks is "Spark plus": the same engine underneath, wrapped in notebooks, managed clusters, Delta Lake as the default table format, and Photon (a native-code execution engine) on newer runtimes. Everything in this guide applies; the notes flag where the wrapper changes your day.

SPARK 4 CHANGED THE DEFAULT THAT BITES ON UPGRADE

Since Spark 4.0, spark.sql.ansi.enabled is on by default. Operations that used to silently return NULL now raise: integer overflow, division by zero, casting "abc" to a number, an out-of-range array index. Stricter and safer — and exactly the kind of thing that turns a pipeline that "worked on 3.5" red the day the cluster upgrades. It's a behavior change, not a bug: fix the data or the cast, don't reflexively set spark.sql.ansi.enabled=false to make the error go away (though that flag does restore the old silent-NULL behavior if you genuinely need a bridge).

stage 03/11 · mental_model · 200/200 tasks · 4.1 s

03 · the mental model

Naive model: "PySpark is pandas with different syntax." Real model: pandas is a calculator; Spark is a factory you send blueprints to. In pandas, every line executes immediately on data in your process. In Spark, your code never touches the data at all — it builds a plan on the driver, and the data lives out on executors that you will never meet personally.

"but it's just Python" — the five reflexes that betray you

It looks like Python and imports like Python, so your pandas muscle memory fires — and every reflex below is correct in pandas and wrong in Spark. This table is the cliff most people walk off in week one.

your pandas reflexwhat it does in pandaswhat it does in Spark
df['x'] = df['y'] * 2mutates the frame in place, nowTypeError — DataFrames are immutable; you must withColumn and rebind
df[df.y > 0] then read a rowruns immediately, row is right therenothing ran — it's a lazy plan until an action; the "result" doesn't exist yet
len(df) / df.shapeinstant, it's in memorydf.count() runs the entire job — there is no cheap row count
for i, row in df.iterrows()slow but worksan anti-pattern with a body count — collect()s everything to one machine, or doesn't run at all
df.loc[5] / df.iloc[0]positional access, freeno row index exists — rows have no stable order or position across partitions

The deeper point under all five: pandas is eager and ordered and single-machine; Spark is lazy and unordered and distributed. Those aren't syntax differences you can paper over with a cheat sheet — they change what's even possible. "Give me row 5" is meaningless when the data is scattered across 200 partitions on 12 machines with no inherent order, and "how many rows?" is a distributed job, not an attribute lookup. When a pandas habit throws a confusing error or runs suspiciously fast, it's almost always one of these five underneath.

THE ONE-LINE TEST

If a line would still make sense when the data is too big for any single computer and split across a cluster, it's Spark-shaped. If it secretly assumes "all the rows are right here, in order," it's a pandas reflex wearing Spark syntax — and it will betray you at scale, not in the demo.

the two-word vocabulary that explains every slow job

Narrow transformations (select, filter, withColumn) work on each partition independently — they chain together into one stage and cost almost nothing extra. Wide transformations (groupBy, join, orderBy, distinct) need rows with the same key on the same machine — so Spark stops, writes every partition's output grouped by key, and every executor fetches its share over the network. That pause is the shuffle: a stage boundary, a disk+network bill, and the place where 90% of your performance problems live.

THE LITMUS TEST

Before running any job, you should be able to answer: how many shuffles does this plan contain, and which line causes each one? If you can't, run df.explain("formatted") and look for Exchange — that's the shuffle, wearing its formal name.

a worked session: pricing quotes at Nimbus Freight

# the cast: shipments (2.1B rows), quotes (400M), dim_ports (4,800)
from pyspark.sql import functions as F
from pyspark.sql.window import Window

# 1 · schemas are contracts — never infer in production code
quotes = spark.read.schema(quote_schema).parquet("s3://nimbus-lake/quotes/")

# 2 · narrow chain: one stage, no drama
active = (quotes
    .where(F.col("valid_until") >= F.current_date())
    .withColumn("value_band",
        F.when(F.col("value_eur") > 1_000_000, "jumbo").otherwise("standard")))

# 3 · the small-table join: broadcast = no shuffle of the big side
enriched = active.join(F.broadcast(ports), "port_id", "left")

# 4 · the big-big join: this WILL shuffle both sides. that's fine — once you know.
priced = enriched.join(shipments.select("shipment_id", "status"), "shipment_id")

# 5 · window: latest quote per shipment — partitionBy = shuffle key
w = Window.partitionBy("shipment_id").orderBy(F.col("quoted_at").desc())
latest = priced.withColumn("rn", F.row_number().over(w)).where("rn = 1").drop("rn")

# 6 · write partitioned by what downstream FILTERS on, not what's convenient
(latest.write.mode("overwrite")
    .partitionBy("region")
    .parquet("s3://nimbus-lake/marts/latest_quotes/"))
DATABRICKS REALITY

display(df) in a notebook is an action (it runs a limit under the hood) and renders a nice table — use it instead of show() there. saveAsTable writes Delta by default on Databricks, which buys you MERGE, time travel, and OPTIMIZE — prefer tables over raw paths on engagements that have Unity Catalog.

first, the word that explains all of this: vectorized

A vectorized operation applies to a whole batch of values in one call, instead of looping one value at a time. The difference isn't style — it's where the work runs. A row-by-row loop runs in the Python interpreter: per value, Python boxes an object, does the op, unboxes it. A vectorized op hands the entire column to compiled code (Spark's JVM, or native libraries underneath) that rips through a contiguous block of memory with no per-row interpreter overhead — often using the CPU's SIMD instructions that genuinely do many values per cycle.

The rule of thumb that follows: 10–100× speed differences between "the same logic" written two ways are normal, not exotic. It's the same reason pandas and NumPy tell you never to loop over rows — and it's the entire reason the next rule exists.

so: built-ins before UDFs, always

# BAD: a Python UDF — rows get serialized to a Python worker and back, row by row.
# Catalyst can't see inside it, so it can't optimize around it either.
@F.udf("double")
def vat(x): return x * 1.24

# GOOD: the same thing, staying in the JVM where the optimizer can see it
df.withColumn("gross", F.col("net") * 1.24)

# NEEDED a real function? pandas_udf works on column batches via Arrow —
# 10-100× faster than a row-by-row UDF, still slower than built-ins.
# pyspark.sql.functions has hundreds of them. Check the docs before writing any UDF.
"PANDAS_UDF" IS NOT PANDAS

The name is a trap. A pandas_udf does not load your data into pandas or run on one machine — it still runs distributed, on every executor, in parallel. What it borrows from pandas is only the function signature: Spark hands each executor its partition as an Arrow-backed pd.Series/DataFrame, your function operates on that batch vectorized, and Spark stitches the results back. So "pandas_udf" means "a vectorized UDF whose body happens to speak pandas," not "do this in pandas." Reaching for it because you "want to use pandas on the cluster" is the misconception — if that's the goal, you want the pandas API on Spark (import pyspark.pandas), which is a different thing again.

Eight repeat offenders, last seen near a cluster you maintain. All previously employed as "the person who set this pipeline up".

★ WANTED ★🧲

The Collect Caller

Crime: collect() on 2.1B rows "to check something". The driver had 16 GB of RAM and one job: it failed at both.

THE FIXPeek with show()/limit(); collect only aggregated results you've counted first.
★ WANTED ★✖️

The Cartesian Joiner

Crime: forgot the join key, produced 400M × 4,800 rows, and described the result as "the job got slower lately".

THE FIXJoins fail loudly without keys only if you let them: check explain() for CartesianProduct before running.

The Schema Inferrer

Crime: inferSchema=True on a 900-file CSV read, every night. Spark reads the data twice and guesses; the guess changed on a Tuesday.

THE FIXSchemas are contracts: define them in code. Inference is for exploration only.
★ WANTED ★🐍

The UDF Maximalist

Crime: wrote @udf wrappers for upper-casing strings and adding numbers. Every row commutes to a Python worker and back.

THE FIXpyspark.sql.functions has hundreds of built-ins the optimizer can see through. UDF is the last resort, pandas_udf the second-to-last.
★ WANTED ★🐼

The Pandas Smuggler

Crime: toPandas() on the full table, "because I know pandas". The cluster did all that work so one machine could fall over with dignity.

THE FIXAggregate in Spark, convert the result. If pandas syntax is the point, the pandas API on Spark exists.
★ WANTED ★📦

The Cache Hoarder

Crime: .cache() on every intermediate DataFrame since 2024. Nothing is ever unpersisted. Executors evict each other in alphabetical order.

THE FIXCache only what's reused by 2+ actions, unpersist() when done, verify in the UI's Storage tab.
★ WANTED ★1️⃣

The Single-File Writer

Crime: repartition(1) before every write "so it's one tidy file". One task writes 600 GB while 199 executors watch in silence.

THE FIXLet Spark write many files; downstream readers don't care. One file is a reporting-tool requirement, not a default.
★ WANTED ★🔁

The Row Looper

Crime: for row in df.collect(): followed by per-row API calls. A distributed engine, used as a slow for-loop with extra steps.

THE FIXThink in columns and joins, not rows. For real per-batch side effects: foreachPartition, carefully.

stage 08/11 · the_eternal_debate · 2/2 tasks · 60 s

08 · the eternal debate: DataFrame API vs Spark SQL

team DataFrame 🐍

"It's testable Python: functions, type hints, IDE refactoring, unit tests per transformation. SQL strings are where logic goes to hide."

Fails when: a 14-deep .withColumn chain reimplements, less readably, what one SQL window expression says.

team SQL 📜

"Everyone reads SQL — analysts, DBAs, the client. The logic is declarative and portable; half the team can review it."

Fails when: 600-line f-string templates with {'{placeholders}'} nobody can test, lint, or refactor safely.

Settled in one sentence, fifty-nine seconds early: they compile to the same plan. df.groupBy("region").agg(...) and spark.sql("SELECT region, ... GROUP BY region") hit the same Catalyst optimizer and produce identical physical plans — performance is a tie, by construction.

THE RULE

Pick per audience, then one job, one dialect. Pipelines that ping-pong between SQL strings and DataFrame chains every five lines are unreviewable in both languages at once. (And never build SQL by concatenating user input — that's not a style question, that's the security finding.)

stage 09/11 · sos_driver_lost · ExecutorLostFailure · retry ∞

09 · SOS — the driver has left the chat

Breathe. Open the Spark UI before touching any config — the answer is almost always written there. Then find your scenario.

"It's been stuck at 199/200 tasks for an hour." — skew

One partition got all the rows because one key owns half the data (at Nimbus: port_id = 'ROTTERDAM', obviously). The UI confirms it: in the stage detail, max task duration ≫ median.

# 0 · find the hot keys — cheap, and now you KNOW instead of guessing
df.groupBy("port_id").count().orderBy(F.desc("count")).show(10)

# 1 · modern Spark fixes most join skew itself — check AQE is on (default since 3.2)
spark.conf.get("spark.sql.adaptive.enabled")            # 'true' or you found the problem
spark.conf.get("spark.sql.adaptive.skewJoin.enabled")   # splits oversized partitions at runtime

# 2 · skewed AGGREGATION (AQE can't always save you): salt the key — works for
#     distributive aggs (sum/count/min/max), NOT countDistinct/median. spread the
#     hot key 16 ways, aggregate, then fold the salt back in
salted = (df.withColumn("salt", (F.rand() * 16).cast("int"))
    .groupBy("port_id", "salt").agg(F.sum("value_eur").alias("partial"))
    .groupBy("port_id").agg(F.sum("partial").alias("total")))

# 3 · skewed JOIN where one side is small-ish: force a broadcast and skip the shuffle entirely
df.join(F.broadcast(dim), "port_id")

"OOM on the driver."

The driver is one machine doing bookkeeping; someone made it do data work. The suspects, in order: collect(), toPandas(), a broadcast() of something that wasn't small, or tens of thousands of tasks generating plan overhead.

# find the collect (it's there): grep first, tune later
grep -rn "collect()\|toPandas()" jobs/

# keep the seatbelt on — this error is the system working as intended:
# "Total size of serialized results ... is bigger than spark.driver.maxResultSize (1g)"
# fix the collect, don't raise the limit. raising it converts a clean error into a dead driver.

"OOM on an executor / ExecutorLostFailure."

One task got more data than its share of memory. Causes in order of likelihood: skew (see above), an explode() that multiplied rows, too few partitions for the data size, or a giant broadcast. Check the stage's spill columns first — spill is the early warning you ignored.

"It worked on the sample, dies on full data."

Of course it did — skew, spill, and broadcast limits are all scale-dependent. Your sample had no hot keys and fit in memory. Re-test with a stratified sample that keeps the big keys (df.sampleBy("port_id", fractions)), and read the full-size plan: AQE may choose different joins at scale.

"The nightly job is suddenly 3× slower and nobody changed anything."

  • The data changed instead. Input grew past the broadcast threshold → a broadcast join silently became a shuffle join. The plan in the UI tells you in one glance.
  • Small-files disease. Upstream started writing thousands of tiny files; listing + opening them dominates. Compact them (Delta: OPTIMIZE).
  • A new hot key arrived. Skew is seasonal — Nimbus signs one mega-customer and a uniform key isn't.

stage 10/11 · boss_fight · 0/5 tasks · awaiting you

10 · boss fight 🐉

Five questions between you and the rank of Catalyst Whisperer. The cluster is watching.

1/5 · Your 40-line transformation chain "runs" in 0.3 seconds. Why?

Lazy evaluation: the chain builds a DAG. The bill arrives with the first action — which is also why the "slow line" in your stack trace is rarely the guilty line.

2/5 · Which of these causes a shuffle?

Wide transformations (groupBy, join, orderBy, distinct, repartition) need keys co-located, so data crosses the network. Narrow ops stay put.

3/5 · df.collect() on a 2-billion-row DataFrame will…

collect() pulls the entire result into driver memory. The 1g maxResultSize default is the seatbelt — fix the collect rather than loosening it.

4/5 · The stage sits at 199/200 tasks for 40 minutes. The most likely cause?

Classic skew signature. Check max vs median task duration in the stage detail, find the hot key with a groupBy().count(), then AQE / salting / broadcast.

5/5 · When does broadcasting a table in a join make sense?

Broadcast = ship the small table to every executor so the big table never moves. Under 10MB it happens automatically; broadcasting something big is a driver-and-executor OOM with extra steps.
