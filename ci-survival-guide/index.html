stage 00/13 · why_this_exists · passed in 0.4s

00 · why this page exists

By now you have a reproducible machine and a history you can't lose. This guide adds the thing that protects everyone else from you, and you from everyone else: the pipeline. Quality gates exist because every developer is an optimist at 17:55 on a Friday — the pipeline is the pessimist you hired to stand at the door. Boring releases are the goal. Boring is praise.

This page will not teach you testing or CI/CD by itself; it covers what that pessimist checks — tests (unit through end-to-end), typing, logging, error handling, and the anatomy of the pipeline itself — for the day it's red and the release is today.

One deliberate choice: this guide is vendor-neutral. Azure DevOps, GitHub Actions and GitLab CI are the same five ideas wearing different YAML. You get the ideas, plus a rosetta table to translate between platforms — not one vendor's syntax reference that rots in a year.

stage 01/13 · the_loop · passed in 1.1s

01 · day zero: the two loops

Everything in this guide serves two nested loops. The inner loop runs in seconds, on your machine: write a failing test, make it pass, refactor. The outer loop runs in minutes, on shared infrastructure: push, watch the stages, review, merge, promote. The inner loop is where you go fast; the outer loop is where the team stays safe.

The same loop, as a session:

# inner loop — runs in seconds, on your laptop
pytest tests/test_surcharge.py -x          # red: the new test fails
# ... write the minimum code that passes ...
pytest tests/test_surcharge.py -x          # green
pytest -q                                  # whole suite still green? refactor freely

# outer loop — runs in minutes, on the CI runner
git push origin feature/quote-totals       # triggers: lint → typecheck → test → build → deploy
IF YOU ONLY REMEMBER THREE THINGS 1. A failing test reproduces every bug before its fix — that is the receipt that the fix works.
2. Artifacts are built once and promoted through environments — never rebuilt per environment.
3. A flaky test is a failing test. A rerun button is not a fix.
stage 02/13 · what_ci_actually_is · passed in 2.0s

02 · what CI actually is

In the 1990s, large teams integrated their code every few months, in a ritual the industry honestly named integration hell: weeks of merging divergent branches and discovering that everyone's "done" code disagreed with everyone else's. The first countermeasure was the nightly build — if the build broke, you knew within a day instead of a quarter.

Extreme Programming in the late '90s pushed the idea to its limit: integrate continuously — multiple times a day, every merge verified by an automated build and test run. Through the 2000s this became tooling (CruiseControl, then Hudson/Jenkins, then everything), and "CI" stopped being a practice you do and became a server you have. Which is roughly when people started confusing the two — the server is just the pessimist; CI is the habit of integrating small and often, so it has something small to check.

Three terms get blended in client meetings. They are different promises:

termthe promisewhere the human sits
Continuous Integrationevery merge to main is built and tested automaticallyhumans merge; the machine verifies
Continuous Deliveryevery green build could ship; release is one approval awaya human clicks "deploy to prod"
Continuous Deploymentevery green build does ship, automaticallyno human in the release path

Most teams that say "we do CD" mean delivery, not deployment. When a client says CD, ask which one — the answer changes the architecture of the last stage.

the worked example: one feature, three tiers

Nimbus Freight charges a fuel surcharge: 18% of shipment value, +4% in peak season (Nov–Dec), +2% over 1000 kg. Here is the same feature tested at all three tiers — note what each tier trusts and what it checks.

# surcharge.py — the unit under test
PEAK_MONTHS = {11, 12}
BASE_RATE = 0.18

def fuel_surcharge(s: Shipment) -> float:
    if s.value_eur < 0 or s.weight_kg <= 0:
        raise ValueError("invalid shipment")
    rate = BASE_RATE
    if s.ship_date.month in PEAK_MONTHS:
        rate += 0.04
    if s.weight_kg > 1000:
        rate += 0.02
    return round(s.value_eur * rate, 2)
# TIER 1 — unit: pure logic, milliseconds, no I/O. trusts nothing, checks the math.
@pytest.mark.parametrize(
    ("ship_date", "weight_kg", "expected"),
    [
        (date(2026, 6, 1),  200.0,  180.00),   # base: 18%
        (date(2026, 12, 1), 200.0,  220.00),   # peak: +4%
        (date(2026, 6, 1),  1500.0, 200.00),   # heavy: +2%
        (date(2026, 12, 1), 1500.0, 240.00),   # peak + heavy stack
    ],
)
def test_surcharge_rates(ship_date, weight_kg, expected):
    s = make_shipment(ship_date=ship_date, weight_kg=weight_kg)
    assert fuel_surcharge(s) == expected

def test_rejects_negative_value():
    with pytest.raises(ValueError, match="invalid shipment"):
        fuel_surcharge(make_shipment(value_eur=-1))
# TIER 2 — integration: the surcharge service against a REAL database in a container.
# trusts the math (tier 1 checked it), checks the wiring: SQL, schema, serialization.
def test_surcharge_persisted_round_trip(quote_repo):      # quote_repo: testcontainers fixture
    quote = quote_repo.create_quote(shipment_id="NF-1042", value_eur=1000.0)
    stored = quote_repo.get_quote(quote.id)
    assert stored.surcharge_eur == 180.00                 # survived the DB round trip intact

# TIER 3 — e2e: hit the running API like a client would. trusts everything below,
# checks that the system is actually assembled. keep these to the critical paths.
def test_quote_endpoint_returns_surcharge(api_client):
    resp = api_client.post("/quotes", json={"shipment_id": "NF-1042", "value_eur": 1000.0})
    assert resp.status_code == 201
    assert resp.json()["surcharge_eur"] == 180.00

the mocking rules

WHERE MOCKS BELONG Mock at the boundaries of your system — HTTP calls, the clock, the filesystem, the database. Never mock your own business logic: a test that mocks fuel_surcharge to test code that calls fuel_surcharge verifies nothing except your ability to type the same number twice.
DON'T MOCK WHAT YOU DON'T OWN Mocking a third-party client (boto3, requests, a vendor SDK) couples your tests to someone else's API shape — they pass forever while the real integration breaks. Wrap the dependency in a thin adapter you own (FxRateClient.get_rate()), mock the adapter in unit tests, and test the adapter itself against the real thing (or a contract test) at the integration tier.

coverage honesty

Measure branch coverage, not line coverage: if peak: rate += 0.04 is one line but two paths, and line coverage is satisfied when you've tested one of them. And remember Goodhart: coverage is a thermometer — the moment it becomes a target, it stops measuring. A team paid in coverage points will produce assert-free tests by Thursday. Use it to find untested code, not to grade developers.

typing: the strictness ladder

pyright's typeCheckingMode goes off → basic → standard → strict (mypy has an equivalent ladder ending in --strict). Start new code at strict; ratchet legacy code up one rung at a time, never down. The placement rule: pydantic at the system's boundaries — parse and validate the outside world once, at the door — and plain typed objects inside, where data is already trusted and validation would just be overhead re-checking itself.

logging that someone can grep at 3am

# structured logging: JSON to stdout — the platform ships it, you don't manage files
import logging, json, sys

def emit(level, msg, **fields):
    record = {"level": level, "msg": msg, **fields}
    print(json.dumps(record), file=sys.stdout)

emit("info", "quote priced",
     correlation_id=req_id,        # the same id flows through every service the request touches —
     shipment_id="NF-1042",        # one grep reconstructs the whole journey
     surcharge_eur=180.00)

Levels that mean something: DEBUG = for the author, off in prod · INFO = business events, one per meaningful action · WARNING = degraded but coping · ERROR = a human should look today · CRITICAL = a human should look now. If everything logs at INFO, nothing does.

error handling in three rules

Raise early — validate at the boundary and fail with a message that names the problem. Catch late — only catch where you can actually do something (retry, translate, exit with a meaningful code — see the setup guide). And never except: pass — that line doesn't handle errors, it hides bodies.

05 · the IDE: stop testing in the terminal like it's 2009

Your IDE will run, debug, and re-run a single test from a gutter icon. This is the inner loop's accelerator pedal:

you want to…VS CodePyCharm

debug a failing assert🐞 on the gutter icon → breakpoint on the assertright-click test → Debug
re-run last failuresTesting panel → Rerun FailedRerun Failed Tests button

The career upgrade hiding in this table: when an assert fails, debug into it — breakpoint on the assert line, inspect the actual objects, walk up the stack. That is strictly more information than the print-spam loop (add print, rerun, add another print, rerun), and it doesn't leave debris in the diff.

BUTTONS THAT BITE IDE test discovery silently binds to an interpreter — not necessarily your project's venv. The classic failure: tests "pass" in the IDE against a stale installed copy of your package while the terminal says otherwise. If IDE and CLI disagree, check the interpreter in the status bar first. Trust pytest in the project venv; the IDE is a convenience view of it, not the truth.

pipeline anatomy — anatomy, not syntax

The YAML below runs nowhere. It exists to name the parts; the rosetta table translates them into your platform's dialect.

# generic-pipeline.yaml — ANATOMY, NOT SYNTAX. every platform has these six organs.
trigger:                       # WHEN: pushes to main + all pull requests
  - pull_request
  - push: [main]

stages:
  - name: lint                 # STAGE: a named phase; fails fast, costs seconds
    steps:
      - run: ruff check .

  - name: typecheck
    steps:
      - run: pyright

  - name: test
    steps:
      - run: pytest -m "not slow" --cov --cov-branch
    cache: ~/.cache/pip        # CACHE: speed only — correctness must survive a cold cache

  - name: build
    steps:
      - run: python -m build
    artifact: dist/*.whl       # ARTIFACT: the build's output, stored once, promoted (fig 2)

  - name: deploy
    environment: prod          # ENVIRONMENT: deploy target with rules attached
    approval: required         # GATE: the human click that makes this "delivery" not "deployment"
    secrets: [PROD_DB_URL]     # SECRET: injected from the platform vault at runtime
    steps:
      - run: ./deploy.sh dist/*.whl

stage 07/13 · testing_the_hard_stuff · passed in 4.1s

07 · testing the hard stuff

The four horsemen of the untestable: time, randomness, the filesystem, and the network. Each has a standard weapon.

time: freeze it

# pip install time-machine   (freezegun is the older classic; both are maintained,
# time-machine is faster — pin whichever you pick)
import time_machine
from datetime import datetime, timezone

@time_machine.travel("2026-12-24 09:00 +0000")
def test_peak_season_detected():
    # inside this test, "now" is frozen at Christmas Eve — peak season, deterministic
    assert datetime.now(timezone.utc).month == 12

Better still: don't let code call datetime.now() deep inside logic. Pass the date in (like fuel_surcharge does with ship_date) and most of your time-testing problem evaporates — the freezer is for the boundary code that remains.

randomness: seed it

rng = random.Random(42)        # inject the generator; tests pass a seeded one.
                               # global random.seed(42) works but is shared mutable state —
                               # the same disease your tests are trying to cure

filesystem: tmp_path

def test_manifest_writer(tmp_path):
    out = tmp_path / "manifest.json"          # real dir, unique per test, auto-cleaned
    write_manifest(out, shipments=["NF-1042"])
    assert json.loads(out.read_text())["count"] == 1

HTTP: mock the wire, not your wrapper's logic

# respx mocks httpx; the `responses` library does the same for requests — match your client
import respx, httpx

@respx.mock
def test_fx_client_handles_rate():
    respx.get("https://fx.example.com/rate/EUR").mock(
        return_value=httpx.Response(200, json={"rate": 1.08})
    )
    assert FxRateClient().get_rate("EUR") == 1.08   # your adapter, real httpx machinery,
                                                    # no network — record/replay (vcr-style)
                                                    # is the alternative for messier APIs

databases: the honest trade-off

in-memory SQLite

Fast, zero infrastructure — and it lies: types, constraints, SQL dialect and concurrency all differ from your real database. Fine for unit-tier repo logic.

testcontainers

Spins up the real database in Docker per test session. Slow to start, completely honest. This is the integration tier.

# pip install testcontainers[postgres]  — the integration-tier fixture
from testcontainers.postgres import PostgresContainer

@pytest.fixture(scope="session")
def pg_url():
    with PostgresContainer("postgres:18.4") as pg:    # pin the version your prod runs
        yield pg.get_connection_url()

Use both, at different tiers — fast liar for logic, slow truth for wiring. Spark/Databricks pipelines have their own version of this whole chapter: the Spark Survival Guide.

stage 08/13 · the_most_wanted · FAILED in 2m04s

08 · the most wanted

Eight repeat offenders. All of them have written code you maintain.

🧸

The Mock-Everything

Crime: mocks their own business logic. The suite is green, fast, and tests nothing; prod burns while 400 mocks applaud.

THE FIX
Mock only at boundaries (HTTP, clock, fs, db). If you mocked something you wrote, delete the mock or the test.
💯

The 100%-Coverage Cultist

Crime: hit the coverage target with tests that call everything and assert nothing. The thermometer reads perfect; the patient is dead.

THE FIX
Branch coverage as a floor (fail_under), code review asks "what would make this test fail?"
😴

The Flaky-Test Snoozer

Crime: made "rerun until green" an official team workflow. The pipeline is now a slot machine with worse odds.

THE FIX
Quarantine marker + tracking issue, root-cause within the sprint. A flaky test is a failing test.
⏰

The sleep(5) Fixer

Crime: "fixes" race conditions by waiting. The race is still there; it just brought a book. CI is 40 minutes slower and still flaky.

THE FIX
Wait on conditions, not clocks: poll-with-timeout for the event you actually need.
🫥

The Assert-Free Test

Crime: calls the function, asserts nothing. Technically a smoke test; mostly just smoke.

THE FIX
Every test states an expected outcome. No assert, no merge.
🚪

The Pipeline Bypasser

Crime: deploys from their laptop, "just this once," for the fourth time this month. Nobody knows which version prod runs, including prod.

THE FIX
Deploys happen from the pipeline only; the artifact registry is the source of truth. Break-glass procedure exists, is logged, and is boring.
🌌

The God Fixture

Crime: one 400-line session fixture every test depends on. Change one field, 90 tests fail, none of them say why.

THE FIX
Small factory fixtures; each test declares only the state it cares about.
🖨️

The Print Debugger

Crime: escaped the setup guide, now debugging CI by adding prints and pushing. Commit log: "debug", "debug2", "DEBUG WHY".

THE FIX
Reproduce locally with the failing test (--lf), use the debugger; in CI, structured logs already hold the answer.
stage 09/13 · the_eternal_debate · passed in 0.9s

09 · the eternal debate: mocks vs real dependencies

team mock

"Real dependencies are slow, flaky, and need Docker. Mock everything; the suite runs in 4 seconds and never fails for fake reasons."

Fails when: the mocks drift from reality and the suite becomes a museum of how the system used to work.

team real

"Mocks test your assumptions, not your system. Run everything against real services; what passes actually works."

Fails when: a 40-minute suite that needs six containers means nobody runs tests before pushing — so nobody runs tests.

Settled in one sentence, sixty seconds early:

THE RULE Fakes at the unit tier, real things at the integration tier, and never mock what you don't own. Both camps are right — at different floors of the pyramid.

10 · SOS — the pipeline is red and the release is today

Breathe. Read the failing stage's log top to bottom once before touching anything. Then find your scenario:

"The same test fails every third run." — flaky-test triage

# 1. quarantine it NOW so it stops blocking everyone — visibly, with a paper trail
@pytest.mark.flaky_quarantine          # custom marker, registered in pyproject
# pipeline fast stage runs: pytest -m "not flaky_quarantine"  + an issue with an owner

# 2. get rerun statistics locally — how flaky is it, and does order matter?
pytest tests/test_dispatch.py -q --count=50    # pip install pytest-repeat
pytest -p no:randomly -q                       # if you use pytest-randomly: does fixed order "fix" it?

3. Root-cause it. Flakiness has exactly five causes — check them in this order: time (midnight/DST/timezone assumptions), ordering (test B depends on test A's leftovers), shared state (module globals, class attributes, reused fixtures), network (real calls hiding in the unit tier), concurrency (actual races — the only genuinely hard one, and the rarest).

"Green locally, red in CI."

The runner is not your laptop. The usual suspects, in order of likelihood:

  • Env vars — your shell exports things the runner has never heard of. Check what the test actually reads; monkeypatch.setenv what it needs.
  • Services — locally you have Postgres running; the runner needs it declared as a service container. "Connection refused" in CI is this, 90% of the time.
  • Parallelism — CI runs -n auto, your laptop doesn't. Two tests writing the same path or table collide only where it's harder to debug. Reproduce locally with -n auto first.
  • Timezone/locale — runners speak UTC and C.UTF-8. Your "works at noon in Athens" date math doesn't.

"The suite takes 25 minutes and everyone hates it."

# profile FIRST — never optimize a suite you haven't measured
pytest --durations=10                # the ten slowest tests; usually 3 tests own 80% of the pain

# then parallelize (pip install pytest-xdist)
pytest -n auto                       # one worker per core — requires tests that don't share state,
                                     # which you wanted anyway

# then split tiers: fast stage on every push, slow stage on merge
pytest -m "not slow"                 # the every-push gate: seconds
pytest -m slow                       # the pre-merge / nightly gate: minutes, allowed

"Coverage gate failed but the code is fine."

Read the diff coverage — which new lines are untested (show_missing = true prints them). Almost always it's a real untested branch in your change: the except path, the else nobody triggers. Write the missing test. Lowering fail_under to ship is borrowing from a loan shark — the gate exists for the next person, who is you in three weeks.

"A secret printed in the logs."

Rotate first. The credential is burned the moment it rendered — logs are archived, forwarded, and screenshotted. Revoke and reissue from the secret store, then fix the masking and add a log-scanning check. (If it also landed in git history, that's the git module's emergency chapter — same rule: rotation beats history rewriting, every time.)

🚨 THE GOLDEN RULE A flaky test is a failing test. Quarantine it with an owner and a deadline, or fix it now — but the rerun button is not a fix. Every push of that button teaches the team that red doesn't mean anything, and a pipeline nobody believes is more dangerous than no pipeline at all.

bonus weapon: Hypothesis 🔮

Property-based testing: you state a property that must hold for all inputs; Hypothesis generates hundreds of adversarial cases and then shrinks any failure to the smallest example. It finds the edge case you wouldn't have written:

# pip install hypothesis
from hypothesis import given, strategies as st

def split_invoice(total_cents: int, parts: int) -> list[int]:
    return [total_cents // parts] * parts        # looks fine. it is not fine.

@given(total=st.integers(min_value=0, max_value=1_000_000),
       parts=st.integers(min_value=1, max_value=20))
def test_split_preserves_total(total, parts):
    assert sum(split_invoice(total, parts)) == total

Falsifying example: test_split_preserves_total(total=1, parts=2)
# integer division ate a cent. Hypothesis found it in milliseconds and shrank
# the failure to the minimal case — 1 cent, 2 parts. invoice math, saved.
