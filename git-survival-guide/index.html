decaf01quickstart

day zero: the loop you'll run forever

Everything else on this page is theory, edge cases, and rescue gear. This is the actual job — the loop you'll run thousands of times. Memorize it, then come back for the rest.

# ── once per project ──────────────────────────────────────
git clone git@github.com:org/repo.git    # existing project (99% of consulting life)
cd repo                                  # (starting from zero instead? git init)

# ── the loop ──────────────────────────────────────────────
git switch -c feature/fuel-surcharge     # 1. branch — never work on main
#    ...edit code...                       2. do the actual job
git status                               # 3. ALWAYS look before you stage
git add -p                               # 4. stage what belongs in this commit
git commit -m "Add fuel surcharge to voyage cost"   # 5. snapshot it
#    ...repeat 2–5 until the feature works...
git push                                 # 6. share it (autoSetupRemote has your back)
#    7. open a PR — on the web, or: gh pr create
If you only remember three things

① Never work directly on main. ② git status before every add. ③ Commit early and often — committed work is the only work Git can save. Everything else, this page can teach you mid-panic.

b7c2914history

what git actually is

Git was born on April 7, 2005 — don't do the math on how that compares to your age — written by Linus Torvalds in roughly two weeks of spite after the Linux kernel's licensing fallout with BitKeeper. It's now old enough to rent a car in most countries and still the default answer to "how do we collaborate on code?"

## the family tree of version control

1. Local VCS (e.g. GNU RCS). Keeps file changes as a series of patches on your machine. Problem: everything is local. It solves "I broke my own file" but not "we are seven people."

2. Centralized VCS (SVN, Perforce…). One server holds all versioned files; everyone checks out from it. You get visibility and access control. Problem: a single point of failure. Server down? Nobody works. Disk corrupted? History gone. Still strictly better than RCS — at least collaboration exists.

3. Distributed VCS (Git, Mercurial). You don't check out the latest snapshot — you clone the entire repository with its full history. Every clone is a complete backup. The server dies? Any laptop on the team can resurrect it.

Plot twist

What do most teams do with their fully-distributed tool? Push everything to one central remote and treat it like a CVCS with extra steps. That's fine — the distribution still buys you offline work, speed, and a backup on every laptop.

## git's design principles

  • Speed — nearly everything runs locally, no network round-trips
  • Simple design — a content-addressable filesystem with a VCS bolted on top
  • Strong support for non-linear development — thousands of parallel branches without breaking a sweat
  • Fully distributed — every clone is the whole repo
  • Handles huge projects efficiently — built for the Linux kernel; your monorepo is fine
c4d88a2mental-model

how git thinks (and why you should stop panicking)

## snapshots, not differences

Most VCS tools store a base file plus a chain of diffs. Git stores a snapshot of your entire project at every commit. If a file hasn't changed, Git just links to the previous identical version. Your history is a stream of snapshots, each addressable by its hash.

## (almost) everything is local

  • No network delay — browsing history, diffing, branching all happen on disk
  • You can work on a plane, off VPN, in a bunker. Commit locally, push later

## integrity & immutability

Everything in Git is checksummed before storage and referenced by that checksum. Git is fundamentally add-only: once you commit, you have to try really hard to permanently delete anything.

The takeaway

If you committed it, it is almost certainly recoverable. So don't panic. The dangerous window is before you commit — uncommitted work has no safety net.

d92b1f7core

the three file states (+ the side drawer)

Every tracked file is in exactly one of three states:

  • Modified — changed, but not recorded anywhere. Zero safety net.
  • Staged — marked, in its current version, to go into the next snapshot.
  • Committed — safely stored in your local database.

## git stash — the side drawer

Not ready to commit, but need to switch context? Stash it. Stash is a side drawer where work-in-progress waits without polluting history.

  • Dirty modified changes blocking a branch switch you don't want to commit yet
  • Staged-but-not-final work — you ran git add but haven't finished the thought
# tuck it away
git stash
# ...switch branches, fight a fire, come back...
git stash pop

## git fetch vs git pull

fetch downloads new commits into your remote-tracking refs and touches nothing else — your working directory stays exactly as it was. pull is fetch + immediately merging (or rebasing) into your current branch. When in doubt, fetch first and look around; it's the read-only option.

## git diff — use whatever shows you the truth

Run git difftool --tool-help to see what UI tools your system offers, use your IDE's built-in diff, or stay in the terminal if you enjoy feeling hardcore.

And the question you'll ask most often — "what did this commit change?" — has two equivalent approaches; know both, because you'll meet both in the wild:

# approach 1 — the single-commit habit: message + diff in one command
git show 4a1f3e0

# approach 2 — the explicit before→after form (~ means "parent of")
git diff 4a1f3e0~ 4a1f3e0

Same output, different superpowers: show is the fast reflex for one commit; the diff A B form generalizes to comparing any two points — branches, tags, "main vs my branch" (git diff main..HEAD).

House rule

Nobody cares whether you use the CLI, an IDE, or a GUI — as long as you can figure out the state of your project through it. The tool is not the skill. Knowing what's modified, staged, and committed is.

## bonus: checkout has been split (and it's a good thing)

git checkout historically did three unrelated jobs — switch branches, discard file changes, and detach HEAD — which is exactly why people kept hurting themselves with it. Modern Git (2.23+) splits the jobs into two commands that can't be confused:

# switch branches (was: git checkout branch)
git switch feature-x
git switch -c new-branch        # create + switch (was: checkout -b)

# discard changes in a file (was: git checkout -- file) — DESTRUCTIVE, no undo
git restore pricing.py
# unstage a file (was: git reset HEAD file)
git restore --staged pricing.py

The old checkout syntax still works everywhere — you'll see it in this guide and all over the internet — but if you're building habits from scratch, build the new ones.

## archaeology: "who wrote this, and WHY?"

Consulting survival skill: you'll spend more time reading inherited code than writing new code. Git remembers everything — ask it:

# who last touched each line of this file (and in which commit)
git blame pricing.py
git blame -L 40,60 pricing.py            # just lines 40–60, less noise

# the pickaxe: find every commit that ADDED or REMOVED this string —
# the answer to "when did this magic number appear and what was the excuse"
git log -S "0.85" --oneline pricing.py

# full history of a file, surviving renames
git log --follow --oneline -- pricing.py

Pro move: when blame points at a reformatting commit, git blame --ignore-rev <sha> (or an --ignore-revs-file) skips it and shows you the real author. The commit message you find at the end of the dig is why the commit message section exists.

## config levels

Git reads configuration from three places; each level overrides the one before:

LevelFileApplies to
git config --system[path]/etc/gitconfigEvery user on the machine
git config --global~/.gitconfig or ~/.config/git/configYou, everywhere
git config --local.git/configThat one repo

## a global config worth stealing

[user]
    name = Your Full Name
    email = your.email@company.com
[core]
    # Prevents "works on my machine" line-ending drama between Windows/Mac/Linux
    autocrlf = input
    # Use a modern editor for commit messages
    editor = code --wait
[init]
    # Use 'main' instead of 'master' to align with modern CI/CD defaults
    defaultBranch = main
[pull]
    # Rebase instead of merge when pulling — keeps history linear and clean
    rebase = true
[push]
    # Auto-set the upstream so you never type --set-upstream again
    autoSetupRemote = true
[fetch]
    # Clean up local refs to branches deleted on the server
    prune = true

[rerere]
    # Git remembers how you resolved a conflict and replays it — rebases get easier
    enabled = true
[diff]
    # Better hunk boundaries; highlights whitespace mistakes
    algorithm = histogram
[alias]
    # A readable graph log to visualize branches
    lg = log --graph --abbrev-commit --decorate --all \
         --format=format:'%C(bold blue)%h%C(reset) - %C(bold green)(%ar)%C(reset) %C(white)%s%C(reset) %C(dim white)- %an%C(reset)%C(bold yellow)%d%C(reset)'
    s = status -s
    st = status
    co = checkout
    hist = log --pretty=format:"%h %ad | %s%d [%an]" --graph --date=short
    uncommit = reset --soft HEAD~1
    # For the brave: commit with a random message from whatthecommit.com
    yolo = "!f() { git commit -m \"$(curl -s https://whatthecommit.com/index.txt)\"; }; f"

## .gitignore

A .gitignore tells Git which paths to never track: build artifacts, virtual environments, IDE settings, OS junk. You can have as many as you want — one per directory, each applying to its subtree — plus a global one for personal noise, configured via core.excludesFile.

# typical Python project noise
__pycache__/
*.py[cod]
.venv/
.env
# IDE / OS junk → better in your *global* gitignore
.vscode/
.idea/
.DS_Store
Thumbs.db
# test & coverage output
.pytest_cache/
.coverage
htmlcov/
Rule of thumb

Project-specific exclusions (build output, .venv) live in the repo's .gitignore so the whole team benefits. Personal-preference exclusions (your editor, your OS) live in your global gitignore — stop pushing your lifestyle choices into every project.

## .editorconfig — the peace treaty

Not a Git feature, but it lives next to .gitignore and prevents half the diffs that shouldn't exist: tabs-vs-spaces wars, trailing whitespace, missing final newlines. Editors pick it up automatically.

## pre-commit hooks — the bouncer at the door

The wanted posters keep saying "use a pre-commit hook" — here's the actual thing. The pre-commit framework runs checks on staged files before the commit lands, so the noise and the secrets never enter history at all:

# .pre-commit-config.yaml — in the repo root
repos:
  - repo: https://github.com/pre-commit/pre-commit-hooks
    rev: v5.0.0
    hooks:
      - id: check-added-large-files    # blocks the 400 MB parquet "oops"
      - id: detect-private-key         # blocks the career-limiting commit
      - id: end-of-file-fixer
      - id: trailing-whitespace
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.8.0
    hooks:
      - id: ruff                       # lint before it embarrasses you in review
pip install pre-commit
pre-commit install        # wires it into .git/hooks — once per clone

From then on, every git commit runs the gauntlet first. Failed check = no commit = nothing to apologize for later. (Pin rev versions to whatever's current — these will age.)

HTTPS + Personal Access Token (PAT). Best for beginners or anyone who doesn't want to touch config. You authenticate with a token, and your OS keychain (via Git Credential Manager) remembers it.

SSH. The "pro" path. A public/private key pair authenticates you — set it up once, never get prompted again.

## advanced: multiple accounts & platforms

The default setup breaks the moment you mix platforms (GitHub, GitLab, Bitbucket) or identities (work vs personal) — Git doesn't know which key opens which vault. The SSH config file fixes it:

# Step A — generate a unique key per identity (don't reuse one key for everything)
ssh-keygen -t ed25519 -C "work" -f ~/.ssh/id_work
ssh-keygen -t ed25519 -C "personal" -f ~/.ssh/id_personal

# Step B — map aliases in ~/.ssh/config
Host github.com-work
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_work

Host github.com-personal
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_personal

# Step C — clone using the alias
git clone git@github.com-work:org/repo.git
git clone git@github.com-personal:username/repo.git

## right email in the right repo: includeIf

Even with auth sorted, you can still commit to a personal project with your work email. Automate the fix with folders plus conditional config:

# ~/.gitconfig
[includeIf "gitdir:~/dev/work/"]
    path = ~/dev/work/.gitconfig-work

# ~/dev/work/.gitconfig-work
[user]
    email = you@company.com

Consultants: scale the same trick per engagement — [includeIf "gitdir:~/clients/<name>/"] per client folder, and the right email follows the repo automatically. No more personal-gmail commits in a client audit trail.

## bonus heist: rebasing a branch that fell far behind

The painful way — git rebase main replays every commit one by one. 15 commits = up to 15 conflict rounds, many on code your later commits already superseded:

A–B–C–D–E   (main)
     └ x1–x2–…–x15   (feature)

Conflict on x1... resolve
Conflict on x2... resolve
Conflict on x3... (you cry)

The fast way — squash first, rebase second:

# Step 1: squash all commits into one
git rebase -i HEAD~15      # mark all but the first as 'squash'
# Step 2: rebase the single commit onto main → at most ONE conflict round
git rebase main
# Bonus — surgical moves: replay only commits after old-base
git rebase --onto main old-base feature
29e5a3bthe-debate

merge vs rebase: the eternal debate, settled in 60 seconds

merge 🤝

Safe everywhere. Creates a merge commit. History shows what really happened, bumps and all.

rebase ✂️

Rewrites history. Clean, linear log. Never on shared branches.

## when to use which

  • Updating your local feature branch with new main commits? → rebase. Clean history, fewer conflicts.
  • Completing a feature and bringing it into main/develop? → merge. Preserves the merge event for posterity.
The one rule that matters

Never rebase a branch other people are working on. Rebasing rewrites SHAs; anyone holding the old SHAs is now living in a parallel universe. Your local feature branch is yours to rewrite freely — a shared branch is not.

3af6b4cSOS

disaster recovery: don't panic 🧯

Breathe. Remember the mental model: committed work is almost never lost. Find your scenario, run the recipe.

## first, know your reset — the three flavors

Half the recipes below use git reset, and the flag is the difference between "all good" and "where did my afternoon go":

CommandBranch pointerStaging areaWorking directory
git reset --soft HEAD~1moves backchanges kept, stageduntouched
git reset HEAD~1 (mixed, default)moves backcleared — changes unstageduntouched
git reset --hard HEAD~1moves backcleared⚠️ OVERWRITTEN — changes gone

Rule of thumb: --soft means "undo the commit, keep my work". --hard means "I want the past back, destroy the present" — committed work survives via reflog, but uncommitted changes swept away by --hard are genuinely gone.

## reset's feral cousin: git clean

reset touches what git tracks. clean deletes what git doesn't — which means no reflog, no recovery, no second chances. Always dry-run first:

CommandDeletesRun it?
git clean -ndnothing — prints what would goalways, first
git clean -fdall untracked files & directoriesonly after the dry run
git clean -fdxuntracked AND ignored: .env, .venv, local data, IDE statelast resort — that -x deletes your secrets file too

## "I committed to the wrong branch"

Oops — you were on main instead of feature-x:

# Option A: reset main back to the remote's state (--hard drops the changes entirely)
git reset --soft origin/main
# Option B: undo the last N commits, keeping changes staged
git reset --soft HEAD~N
# Either way — your changes are now staged. Put them where they belong:
git checkout -b feature/my-changes
git commit -m "committing on the proper branch"

You can also cherry-pick + revert if you want to preserve history instead of rewriting it.

## "I deleted untracked files!"

# Untracked = git never knew them. Your hopes, in order:
# 1. Your editor's local history (VS Code: Timeline view / "Local History:
#    Find Entry to Restore"; JetBrains: right-click → Local History → Show History)
# 2. Anything that was ever STAGED may survive as a dangling blob:
git fsck --lost-found        # then inspect .git/lost-found/ for your content
# 3. OS backups (Time Machine etc.) — the last resort

Sometimes the honest answer is: it's gone. The durable fix is a habit, not a command — commit early and often on a branch. WIP commits are free; you can squash them later.

## "I committed a secret!"

# Haven't pushed yet? Fix the file, then fold the fix into the last commit:
git commit --amend --no-edit
Pushed already?

ROTATE THE SECRET. NOW. Before any git surgery. Once it touched a remote, assume it's compromised — cleaning history is housekeeping, rotation is the actual fix. Then see "you pushed your mistake" below. One platform reality: on Azure DevOps, rewriting a branch with policies requires the Force Push permission — typically a repo admin, not you. One more reason rotation is the fix and history surgery is just hygiene.

## "I accidentally deleted my branch!"

You thought you'd merged it, deleted it, and then realized you needed that code.

# 1. find the commit hash of the "lost" work
git reflog
# 2. spot the last commit message you remember
# 3. resurrect it on a new branch
git checkout -b recovered-branch <commit-hash>

What reflog actually shows you — a diary of everywhere HEAD has been:

$ git reflog
4a1f3e0 HEAD@{0}: checkout: moving from feature-x to main
8b2c915 HEAD@{1}: commit: add vessel config parser   ← there it is
1c9d042 HEAD@{2}: commit: wire up sensor mapping
7e3af80 HEAD@{3}: branch: Created from main

Reflog records every move for ~90 days by default — which is why "permanently deleted" in Git usually means "I haven't looked in the reflog yet."

## "I'm stuck in a merge/rebase conflict and everything is broken!"

The terminal says (main|REBASING 1/5) and your files are full of <<<<<<< HEAD:

git merge --abort
# or
git rebase --abort

Both return you to the state before the operation started. Not sure how a merge/rebase will go? Take a backup branch first — it never hurts: git branch backup-before-rebase.

## actually resolving the conflict (abort is not a lifestyle)

Sooner or later you have to go through, not around. Conflict markers are just three labeled regions:

<<<<<<< HEAD                          ← your side ("ours")
price = base * 1.24
=======
price = base * 1.20
>>>>>>> feature/new-vat              ← incoming side ("theirs")

The four-step ritual:

# 1. see which files are conflicted
git status
# 2. open each file, decide what the code SHOULD say
#    (keep ours, keep theirs, or write something new) and delete ALL markers
# 3. tell git the file is resolved
git add pricing.py
# 4. continue the operation
git merge --continue      # or: git rebase --continue
Heads-up on rebase conflicts

During a rebase, "ours" and "theirs" feel swapped: you're replaying your commits onto main, so HEAD ("ours") is main's side and "theirs" is your own work. If a conflict resolution looks backwards, this is why — read the code, not just the labels.

## "I messed up my last commit message (typo)!"

git commit --amend -m "The correct message"

Careful: if you already pushed, this rewrites history and needs a force push. Never on a public/shared branch.

## "undo a pushed commit — politely": revert

The recipes above rewrite history, which is forbidden on shared branches. revert doesn't rewrite anything — it adds a new commit that is the exact inverse of a bad one:

# find the offender
git log --oneline
4a1f3e0 Add fuel surcharge        ← this one broke prod
8b2c915 Wire up sensor mapping

git revert 4a1f3e0
# → new commit: "Revert 'Add fuel surcharge'" — history intact, damage undone
git push                          # plain push. no force. no team meeting.

This is the default answer for "bad commit on main": the mistake stays visible in history (honest!) and nobody's clone breaks.

## "I need that one commit over there": cherry-pick

A fix landed on the wrong branch, or you need a single commit from a colleague's branch without taking the rest:

git switch release/1.3            # go where the commit SHOULD be
git cherry-pick 4a1f3e0           # copy that one commit here (new SHA, same change)

Classic use: a hotfix made on main that the release branch needs too. Note it's a copy — the commit now exists twice with two SHAs, which is fine occasionally and a mess as a lifestyle. If you're cherry-picking constantly, your branching strategy is filing a complaint.

The golden rule of git recovery

If you have pushed your mistake to the server, talk to your team before you 'force push' a fix. git push --force rewrites history for everyone. It is the one command that can truly cause a disaster for others.

## you pushed your mistake — the options menu

  • git revert <commit-hash> — a new commit that undoes the old one. Pro: safe, doesn't rewrite history. The default answer on shared branches.
  • git push --force-with-lease — the polite force push: refuses to clobber commits you haven't seen. Pro: clean history. Con: still never on main or shared develop.
  • git-filter-repo — the nuclear option: erase all traces of a file from the history of every branch. Everyone must delete their clones and re-clone. Pro: the mistake is genuinely gone. Con: disrupts the whole team. Reserve for leaked secrets.

## bonus weapon: git bisect — "WHEN did this break?"

Something broke, you don't know which of the last 60 commits did it, and reading diffs is for people with free evenings. Bisect binary-searches your history for you:

git bisect start
git bisect bad                 # current commit is broken
git bisect good v1.2           # this old tag/commit was fine
# git checks out the midpoint — you test, then say:
git bisect good                # or: git bisect bad
# repeat ~6 times for 60 commits (log₂!) until:
4a1f3e0 is the first bad commit
git bisect reset               # back to where you started

If you have a test command, git bisect run pytest tests/test_pricing.py automates the whole hunt while you get coffee.

4b07c5dworkflow

pick your branching strategy

Day-one question

On any new project or team, always ask: "What git strategy do you use?" Before you push anything.

## 🏃 GitHub Flow — keep it simple

Branch from main → short-lived PR (1–3 days) → merge → deploy immediately. Main is always deployable. No long-running branches.

Best for: web apps, SaaS, small teams.

## 🏛️ GitFlow — rigid and safe

main + develop + feature + release + hotfix branches. Structured and predictable.

Best for: versioned products, scheduled releases, regulated industries.

Watch out for: the overhead is real — long-lived branches invite merge hell.

## 🚄 Trunk-Based Development — high velocity

Everyone integrates to trunk daily. Branches live hours, not days. Feature flags hide work-in-progress.

Best for: high-trust teams with great CI/CD — the fastest possible integration cycle.

Watch out for: needs excellent test coverage and CI. Risky without both.

Most teams run a modified version of one of these. Reading list in the resources.

## wait — what's a tag? (the diagram owes you this)

That tag v1.3 in the GitFlow diagram: a tag is a permanent, human-readable bookmark on one commit. Branches move with every commit; tags never do — which is exactly what you want for marking releases:

git tag -a v1.3 -m "Release 1.3: fuel surcharge support"
git push --tags                # tags don't push by default — everyone forgets this once
git checkout v1.3              # time-travel to exactly what shipped (detached HEAD — look, don't build)

GitHub/GitLab "Releases" are tags with release notes and artifacts attached. If your CI deploys on tags, the tag is the release button — treat it with the same respect.

5c18d6ecollaboration

the PR review

A pull request is a conversation with your team, not a paperwork ritual. Open it in draft mode early — even the moment you start. By the time you mark it ready, it should explain:

  • The Why — what problem are we solving (a ticket reference counts)
  • The How — a high-level summary of the approach
  • The Risk — what could this potentially break
  • The Evidence — screenshots for UI, log snippets, or "I ran X and got Y"

## commit messages humans can read

Your reviewer reads the commit list before the diff. Anatomy of a message that helps instead of haunts:

Add fuel surcharge to voyage cost calculation      ← imperative mood, ≤50 chars,
                                                       no trailing period

← blank line (mandatory — separates subject from body)
Charterers are billed surcharge per region since the
May contract update. Without this, invoices for ECA
zones under-report by ~4%.

Refs: DS-1042                                       ← body wraps at 72, explains
                                                       WHY, not what (the diff
                                                       already shows what)

The litmus test for the subject line: it should complete the sentence "If applied, this commit will…". "If applied, this commit will add fuel surcharge to voyage cost calculation" ✓. "If applied, this commit will fixed stuff" ✗ — and now you understand the Nervous Committer poster.

## the merge button: three flavors, one decision

The merge-vs-rebase debate you actually face daily is a dropdown on the PR page. All three buttons land your code; they write different history:

ButtonWhat main's history getsUse when
Merge commitAll your branch commits + a merge commit joining themThe individual commits are clean and worth keeping (you squashed locally like a pro)
Squash & mergeONE commit, no matter how messy the branch wasThe team default in most places — it forgives the Nervous Committer and keeps main readable: one PR = one commit
Rebase & mergeYour commits replayed onto main, no merge commitYou want every commit preserved AND a linear history — demands discipline from everyone
Day-one question, part 2

Right after "what git strategy do you use?", ask "and which merge button?" Teams that squash-merge care less about your branch hygiene; teams that merge-commit will read every commit you push. Calibrate accordingly.

## self-review checklist (before you ping anyone)

  • Does the code pass local tests?
  • Did I remove all the print() debugging and stray TODO comments?
  • Are commit messages clear, descriptive, and squashed where needed?
  • Did I rebase against develop/main so there are no conflicts?
  • Would I be happy to maintain this if I saw it for the first time?

6d29e7fboss-fight

boss fight 🐉

Five questions stand between you and the rank of Reflog Necromancer. No reflog can save you from a wrong answer — but the explanations can.

1/5When is it OK to git push --force?

Your own un-shared branch is yours to rewrite. --force-with-lease refuses to clobber commits you haven't seen. If others may have pulled it: Golden Rule — talk to the team first.

2/5You've been committing to main for two hours. First move?

Your work is local and committed = safe. Soft reset returns the changes to staged, then git checkout -b feature/proper-branch and commit there. No deleting, no panicking, no lying.

3/5Why do we gitignore .venv folders?

Platform-dependent binaries + gigabytes of installable packages = repo bloat and guaranteed "works on my machine" breakage. The lockfile is the source of truth; the venv is disposable.

4/5Updating your local feature branch with new main commits — which tool?

Rebase for updating your local feature branch; merge for landing the finished feature into main/develop. And option d is how the workshop series got its name.

5/5git fetch vs git pull — fetch is…?

Fetch is read-only reconnaissance. Pull = fetch + immediately merge/rebase into your current branch. When in doubt, fetch first and look around.
